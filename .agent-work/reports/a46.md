# A46 candidate ordering and hierarchical budget reservation

Branch: accuracy/a46
Starting integration commit: 966f80b
Author: J.C. Vaught <jvaught@sc.edu>

## Scope

The internally generated v2 grid lattice is reordered before scoring. Known-water positions are evaluated first. Unknown coverage and land positions remain in the stream and are reported by the existing scorer. Within each disposition, occupied spatial bins are traversed with a deterministic bit-reversed order and round-robin fill, so an early prefix spans the declared domain. The exact candidate set is preserved and no candidate is pruned. Explicit candidate streams retain caller order for fixed-candidate parity.

The new module exposes order_candidate_positions(positions, *, water_status=None, bounds=None, bins_per_axis=None) and iter_ordered_candidate_positions with the same keyword arguments. The helper preserves duplicate input positions and uses O(1) deque removal while emitting each position.

The v2 hierarchical path uses the same ordering for internally generated stages and allocates ceil(remaining_budget / stages_left) candidates to each stage. The initial coarse stage therefore reserves a deterministic share for refinement. Explicit candidate streams retain caller order. Stage truncation is tracked separately from refinement continuation, omitted planned candidates are consumed after planned stages to keep counts within the declared budget, and budget exhaustion is reported only when a novel planned candidate remains beyond that budget. Candidate scores continue through CandidateScorer, including unknown coverage outcomes and complete objective decomposition. The result remains heuristic with certificate_scope none.

## GPU integration boundary

The shared reorderer is available to both CPU and GPU scorer callers, but the current v2 CLI GPU grid branch directly calls score_candidate_positions_batched on enumerate_grid_points. A small coordinator-owned change is required there: import order_candidate_positions, reorder enumerate_grid_points with scorer.vector_map.point_water_status and config.bounds_xy, then pass that ordered tuple to score_candidate_positions_batched. This keeps CPU and GPU candidate consumption identical without changing GPU scoring ownership.
