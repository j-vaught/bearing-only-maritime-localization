# Assignment expansion parallelization review

**Scope**

This source review used commit `a9ac9f202c2f53f5adcf2df12fff4e3c649f7d10`. It did not run tests, profiling, timing, or device work, and it made no changes to the diagnostic or production code. The review treats the reported workload of roughly 22,000 branches across 64 modes as a planning input, not as measured performance evidence.

**Current branch boundary**

`bearing_localization/search/assignment_expansion.py` enumerates branches deterministically by `(report_index, catalog_key)`, assigns each an integer `branch_id`, enforces `max_branches`, emits start and result callbacks, and reports visited and unvisited counts. Each branch freezes at most the current assignments plus one proposed report and catalog record. Its SciPy residual evaluates the projected observer position through a CRS inverse transform, then computes each initial true-north bearing with `pyproj.Geod.inv`. It wraps the angular error and divides by that individual observation sigma. A converged pose is sent to `CandidateScorer.evaluate`, which owns final water validity, visibility, group formation, type likelihood, and complete report-to-group assignment. That canonical score is the acceptance authority.

The branch fit and exact score are currently combined in `_fit_branch`. A parallel implementation should first split the fit from canonical evaluation. The fit can become a pure worker operation because its inputs are a small frozen bearing set and bounded pose window. The coordinator should retain the `CandidateScorer` and run its exact evaluations. This avoids copying the map, catalog, spatial index, and mutable scorer state for every fit task, and it keeps map and assignment semantics unchanged.

**Stage one with CPU workers**

Add an immutable `ExpansionFitTask` and `ExpansionFitResult` in `bearing_localization/search/assignment_expansion.py` or a focused sibling module. The task should carry a mode identifier, stable branch identifier, report index, catalog key, seed pose, clipped lower and upper bounds, target longitude and latitude pairs, observed bearings, individual sigmas, source CRS, and `max_nfev`. A worker initializer should construct and retain the CRS-to-geographic transformer and WGS-84 geodesic object. Each worker should run the same bounded `least_squares` method and FP64 geodesic residual used now. The result should include proposal pose, solver status, function and Jacobian evaluation counts, residual evaluation count, and a structured failure status. Canonical scoring should remain on the coordinator in stable branch order.

Use explicit branch identity across modes. A run-level key can be `(mode_index, branch_id)` while the within-mode branch ID remains the existing index after deterministic sorting. Record the candidate-pool digest and seed identity with each mode so a replay can prove it used the same branch plan. Apply the branch budget before dispatch to the first `max_branches` entries of the complete ordered plan. Do not use worker completion order to select branches or adjust the cap. Keep unvisited counts equal to the plan size minus the explicitly completed or dispatched IDs according to documented ledger states.

Batch tasks by mode or a bounded number of branch IDs to reduce process messaging, while limiting in-flight work by both task count and serialized bytes. Preserve one ledger event per planned branch, including `not_dispatched`, `worker_failed`, and `cpu_fallback` outcomes where applicable. The coordinator alone should call progress and result callbacks. Worker startup failure, process death, or malformed output should cause identified affected branches to be retried serially when the configured policy permits. Otherwise the result must be incomplete and expose every failed or outstanding branch. No callback or process error should silently erase a branch.

`bearing_localization/search/parallel_candidates.py` provides reusable patterns for persistent spawn workers, bounded queues, stable IDs and sequence order, explicit error counts, and worker memory reporting. Its worker owns a `CandidateScorer`, so it should not be reused wholesale for fit tasks. `bearing_localization/search/parallel_screened.py` provides a useful disposition ledger for completed, failed, outstanding, and not-dispatched work. The new fit worker should avoid serializing `CandidateScorer` and its full map payload. Candidate scoring can be parallelized separately only if later measurements show it dominates and the exact scorer can be instantiated safely within bounded persistent workers.

**Stage two with batched device proposals**

The present device angular kernel in `bearing_localization/backends.py` computes projected-plane bearings. Its FP64 rebasing before FP32 arithmetic protects local differences at large coordinate offsets, but it does not convert a projected direction into the exact WGS-84 initial azimuth produced by `Geod.inv`. It therefore cannot replace the current residual without a proven coordinate-specific angular error envelope. `bearing_localization/search/gpu/costs.py` consumes CPU-prepared true-north bearings to evaluate likelihood costs; it does not fit poses or provide geodesic derivatives. The full canonical scorer also still needs CPU map visibility and assignment evaluation. Moving only a small likelihood calculation to the device is unlikely to remove those costs by itself.

A future device fitter would require a new, bounded batch solver rather than wrapping the current adaptive SciPy calls. For each mode, the CPU should prepare immutable branch inputs and submit fixed-size tiles. A device kernel could evaluate residuals and finite-difference Jacobians for each branch, with per-branch trust-region state, iteration count, and `max_nfev`. Every temporary must be sized from a configured `max_batch_bytes`; do not form a tensor over all modes, branches, observations, and catalog records. The implementation must preserve each branch ID even when it is padded, rejected, or falls back. Exact candidate-pool construction, geodesic offsets, sigma construction, and final scoring remain CPU responsibilities.

Before a device approximation can influence a fitted proposal, compare its per-observation angular residuals against the FP64 `Geod.inv` reference throughout the full local search box, for every target range and applicable CRS. The agreement limit is `min(0.001 degrees, 0.01 * observation_sigma_deg)` for each bearing. Validate Jacobians and fitted poses as well as residual values, because a small residual error can still change an ill-conditioned solution. A failed or unavailable device must rerun all affected branches through the unchanged CPU fit and preserve the fallback reason in the ledger. If the error bound cannot be established, the device path may be used only for proposal ordering; every branch that can affect final acceptance still requires CPU fitting and canonical scoring.

The alternative is a device implementation of a geodesic azimuth kernel. That would need a carefully validated ellipsoidal inverse solution and derivatives, including behavior near singular geometries. It is a separate numerical implementation with a larger verification burden than the current projected-angle kernel and should not be inferred from planar parity tests.

**Measurements and verification for a later implementation**

Once the active real-data run releases its shared benchmark lock, collect phase timings separately for candidate-pool preparation, frozen-target preparation, solver residual calls, canonical scorer calls, map line-of-sight checks, group assembly and report assignment, process setup and messaging, and callbacks or artifact writes. Include device initialization, host-to-device and device-to-host transfers, synchronization, and fallback work in any device end-to-end result. These measurements determine whether CPU fit parallelism or canonical-scoring parallelism is the relevant next step. This review makes no speedup claim.

Add `tests/accuracy/test_assignment_expansion_parallel.py` with deterministic fixtures. It should compare serial and worker branch plans, IDs, candidate-pool digests, ledger coverage, statuses, and exact canonical winners and assignments. Proposal coordinates should be compared under a stated numerical tolerance, while exact CPU scores and assignment sets remain the parity check. Exercise empty and budget-limited plans, deterministic ordering despite out-of-order worker completion, worker initialization failure, worker death, serial fallback, callback exceptions, and bounded in-flight memory. For a device prototype, additionally test large global coordinates, wrapped bearings, heterogeneous sigmas, empty batches, repeated-buffer reuse, maximum batch memory, angular error bounds across the complete search box, and CPU fallback. Existing `tests/accuracy/test_assignment_expansion.py` and `tests/accuracy/test_assignment_expansion_review.py` already cover deterministic candidate ordering, callback and budget semantics, branch outcomes, and canonical reassignment; preserve their contracts.

**Future edit map**

The first implementation should modify `bearing_localization/search/assignment_expansion.py` to expose immutable fit tasks, fit results, and a serial fit adapter while keeping the public `expand_assignments` behavior stable. A new `bearing_localization/search/parallel_assignment_expansion.py` can own worker lifecycle, bounded dispatch, ordered result collection, fallback, and ledger state. A later scorer-parallel stage may extend `bearing_localization/search/parallel_candidates.py`, but only with profiling evidence and exact-output parity. A distinct device solver should live beside `bearing_localization/search/gpu/costs.py`; it must not be presented as a geodesic implementation by reusing `angular_cost_cupy`. Tests belong in `tests/accuracy/test_assignment_expansion_parallel.py`, with additional device tests kept optional on CPU-only systems and required on the target device before enabling that backend.
