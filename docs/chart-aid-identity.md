# One chart aid per location

Simulator and search now share the same chart-aid identity rule. Source records at exactly equal parsed latitude and longitude values represent one physical object. Grouping crosses chart names, scale bands and component labels. It uses numeric equality rather than a distance threshold or rounded coordinates. Beacons, lights, daymarks and topmarks at a point therefore share one object, with other recognized navigation components retained under that object. Vessels and virtual aids remain separate.

The shared step adds exact-coordinate consolidation to the combined ENC importer's existing named physical-aid grouping. That earlier importer can also link named components using chart/proximity metadata. This change does not remove those prior links or claim that the whole importer uses coordinate equality alone. Nearby distinct source points remain separate at the new consolidation step.

Merged keys encode the exact coordinate values, so input order and source-feature naming do not change their physical identity. Single source records retain their original keys. Complete original CatalogRecordV2 records, including metadata and provenance, are retained under the versioned source_components schema. Earlier importer component lists remain inside those complete snapshots. Repeated canonicalization does not nest duplicate snapshots or create additional objects. Existing singleton identity warnings and cross-location alias ambiguity remain intact.

Object identity and positional certainty remain separate. Known position bounds and angular extents are aggregated conservatively, unknown bounds remain unknown, and unsupported or conflicting component offsets disable exact geometry support. Simulation rejects unsupported merged observation geometry rather than silently selecting a point. Grouping a radio or signal component does not establish that it is a visually classified channel marker; unknown source types remain unknown unless the same object contains a recognized physical aid. The numerical flags remain enabled for genuine distinct-object ambiguities.

PhysicalSceneV2 canonicalizes catalogued and uncatalogued chart components before targets, range, visibility, angular grouping, misses or bearing noise are generated. CPU prediction contexts, scoring, pruning projection and search sessions use the same records. Externally supplied geographic indexes must match the canonical keys and coordinates. Catalog identity memoization assumes the catalog and its nested metadata/provenance remain read-only, matching prepared-context reuse.

Resident searches retain the original prepared-world cache unchanged. A separately keyed object-only view copies and consolidates catalog rows, normalizes component types and rebuilds only the object tree. All shoreline arrays and barriers are reused by reference. The sidecar stores only objects, keys, object-tree arrays and scalar flags. Its identity binds the base cache key, source catalog, canonicalization policy, implementation and object-type taxonomy. Integrity checks, locking and atomic writes protect reuse. The default object-cache directory sits beside the resolved base cache, keeping the existing HDD storage arrangement.

The resident CLI applies this view automatically, and --optimized selects the reviewed true-bearing pruning, parallel prediction and cooperative matching path. Low-level callers loading a raw PreparedWorld must call aid_view.load_or_canonicalize or canonicalize_prepared_world before constructing their device. Raw preparation still preserves the original input rows. Its imported position/offset primitives remain unchanged; exact source-revision compatibility pins preserve that raw cache identity for CPU runtime-only edits. Canonical object data receives its own identity and never masquerades as the original raw cache.

The conversion command is uv run python tools/canonicalize_chart_aids.py INPUT OUTPUT. JSON and gzip-compressed JSON are supported. It requires a separate new output file. The canonical NOAA catalog is saved in data/objects-chart-aids-canonical.json.gz, alongside its unchanged source. The 64,400 source records become 32,168 chart objects. The 243 auxiliary-only groups retain unknown classification; 31,925 groups contain recognized physical aids. Every original source record, metadata value and provenance field is retained losslessly. Counts and checks are recorded in [the catalog record](verification/chart-aid-canonical-catalog.json).

The [verification record](verification/chart-aid-identity-checks.json) covers 144 passing focused tests and preservation checks. A synthetic GPU3 case gives one simulator target, one search object, complete matching, status consistent and zero numerical flags. A tiny two-process CLI check evaluates five regions and four terminal cells; its second process forbids both raw preparation and object-view rebuilding and successfully reloads both caches. These are identity, correctness and cache-lifecycle checks. They do not recover Charleston or establish a localization error in meters.

The existing long run continues with its original observations and loaded code. Its saved cache archive, key and modification time remain unchanged. No new Charleston or coast-wide search was launched for this change. A blind accuracy check with newly generated canonical observations remains the next separately approved experiment.
