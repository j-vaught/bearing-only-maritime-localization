# A14 exact-scoring next step

## Evidence boundary

This is a read-only diagnosis from the saved cached-candidate profile at `03ee598` and A22 same-sample result at `3a1ac8b`, plus the corresponding exact source paths. No new timing run or truth data was used. The cached profile covered 66,668 catalog records and 255 selected candidates. Direct exact scoring took 28.934 s at one worker and 25.496 s at four workers; 131 candidates received scores. A separate 2,048-candidate scaling sample recorded 51.227 s steady at one worker, 14.530 s at four, and 8.136 s at eight. These are shared-host diagnostics, not clean-host throughput claims.

A22's same-255 comparison took 18.238 s for direct exact evaluation versus 23.025 s for screen-first evaluation. The screened path performed 170 exact evaluations and pruned 85, while direct exact evaluated all 255; both retained the same best score and tie ID. The screen path performs a complete visibility scan before it can prune. Its measurement stored no per-candidate ray counts, exact geodesic-call counts, or phase timings, so the saved artifacts do not establish that LOS is the dominant cost for every exact candidate. The proposed operation reduction below follows from the code path and must be measured in a separately approved run.

## One exact-preserving optimization

Add an index query variant that returns each accepted catalog index together with the exact inverse-geodesic initial bearing and distance already computed during radius filtering. In `maritime_localization_shared/geospatial/spatial_index.py`, `GeographicSpatialIndex.query_radius` calls `_GEOD.inv` for each ECEF-prefilter hit and discards the returned bearing and distance, retaining only indices. In `bearing_localization/search/prediction.py`, `predict_visible_groups` then calls `geodesic_bearing_distance` for every nearby physical record. For a record with the supported nominal-zero visible-feature offset, that is a second WGS84 inverse for the same observer and catalog point. The `coordinates.py` helper uses WGS84 `Geod.inv` too, and converts its initial azimuth modulo 360 degrees.

The query radius is `visibility_radius_m + max_offset_m`; the predictor still has to apply the configured inclusive or exclusive minimum/maximum range to the actual target. For zero-offset records, the query's exact bearing/distance are exactly the values needed for that range test and angular detection. For nonzero calibrated offsets, the target point differs, so prediction must retain its existing forward offset and second inverse. Unsupported-offset records remain unresolved as today. The optimization therefore removes one exact inverse per returned physical record with zero offsets, without changing query membership, range edges, target projection, line of sight, merge semantics, or objective. Its maximum affected record count is bounded by the nearby physical zero-offset records; actual counts were not retained in either profile.

The index API should preserve `query_radius` unchanged for other callers and expose a sibling geometry-returning query. It should validate and sort candidates exactly as the current method does, use the same `_GEOD` object and inclusive `distance_m <= radius_m` test, and return the same stable catalog order. Prediction can use cached inverse geometry only when both prepared east and north offsets are exactly zero. Existing `geodesic_bearing_distance` remains the path for nonzero offsets.

This is a CPU geometry optimization. GPU execution does not naturally accelerate scalar `pyproj.Geod.inv`, exact range gates, or GEOS LOS predicates; moving these calls to a different numeric backend risks changing geodesic and boundary behavior. Any later GPU work should remain limited to the already separated cost-matrix or assignment stages and retain their exact parity checks.

## Mathematical note on skipping LOS

The proposed idea of treating any in-range catalog object as a possible match while omitting missed-prediction costs does not appear to add a tighter supported bound than A21's current no-count relaxation. `candidate_objective_lower_bound` already permits zero residual and type factor one for each report, minimizes the global report match floors against clutter over assignment cardinalities, and adds mandatory missed-group cost only when a certified visible-group minimum `K` is supplied. Setting `K = 0` removes that missed-group term and allows predicted bearings to be more favorable than any particular in-range catalog list. A catalog-constrained pre-LOS relaxation would need to prove its per-report cost floors account for merged representatives, uncertainty from group metadata, type factors, and one-to-one assignment; without that proof it should not prune. As written, allowing arbitrary in-range objects is likely subsumed by A21's catalog-independent report floors rather than a new bound.

## Acceptance checks for a future implementation

Keep the current scorer path as an oracle and compare the complete `PredictedGroupSet`, `CandidateEvaluation`, and exact score for existing A14 fixtures plus a catalog with mixed zero and nonzero calibrated offsets. Include records exactly at inclusive minimum and maximum range, an ECEF prefilter candidate rejected by the exact radius check, duplicate catalog coordinates with distinct keys, north-crossing bearings, and catalog order permutations. Assert that the old and geometry-returning index queries produce identical ordered indices, and that cached bearings/distances equal `geodesic_bearing_distance` exactly for zero-offset records. Separately assert unchanged handling for nonzero and unsupported offsets and all existing LOS/coverage cases.

Instrument only an approved later profile to record ECEF prefilter hits, radius-returned physical zero-offset records, nonzero-offset records, exact inverse calls, LOS rays, and per-candidate scoring phase time. First confirm the inverse-call reduction equals the count of returned physical zero-offset records. Then compare direct exact scores and visible-group metadata under the frozen 255-candidate sample and the saved 2,048-candidate sample. No performance or accuracy claim follows until those measurements pass parity and show a repeatable runtime benefit.
