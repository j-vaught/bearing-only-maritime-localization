# A43 Pairwise Proposal Feasibility Profile

## Scope and source audit

This was a read-only production audit plus one bounded CPU cProfile run. The three A26 pairwise/budget-64 attempts remain preserved in their original run folders; two timed out at 300 seconds and the third was interrupted at 82 seconds for the reserved profile window. No attempt was overwritten.

In `bearing_localization/search/proposals/pairwise.py`, `generate_geographic_pairwise_proposals` traverses report pairs outside sorted catalog source/target pairs (lines 262–352). For each source it queries all catalog keys within inclusive `2 * max_range_m`, then retains only target keys lexically greater than the source key. It recomputes exact WGS84 pair inverse, geodesic midpoint, local frame, and source/target local coordinates for each report pair. It evaluates both target assignments and retains exact WGS84 candidate-to-object range checks. Stable proposal IDs derive from observation indices and assigned catalog keys. The shared geographic index uses ECEF cKDTree broad-phase followed by exact inclusive WGS84 inverse distance filtering in `maritime_localization_shared/geospatial/spatial_index.py` lines 202–228. The implementation has no source or neighbor caps.

The proposal limit is checked only after a geometrically valid candidate passes exact range checks. Thus budget exhaustion may require work over many invalid pairs. The pairwise runner drains generated proposals before scoring and forwards emitted count as budget usage; the scorer separately deduplicates candidate positions. This makes proposal-budget semantics distinct from unique scored-position count and should remain unchanged in this optimization.

## Bounded profile

The profile used the frozen A26 5 km/types-off/budget-64 development row: measurements `port-001/placement-001/r1/5000m/types-off/nominal`, catalog SHA-256 `2554a1f6e574b6b9ffdefe6bb7b96636d756c9cbd87018be8f7e078738227704`, and map SHA-256 `cce049c5911b39072d30f26c09947782a78e350e65a3f69c6923312fba3f9d93`. The watchdog stopped profiling at 30.04 seconds and saved a partial profile at `.agent-work/outputs/a43-pairwise-profile/5km-types-off-budget64/profile.prof`, summary `profile.txt`, and metadata `profile.json`. The run did not produce a complete estimate or telemetry; counts below describe only work observed before the watchdog.

In the partial profile, the full CLI path accumulated 29.352 seconds in `search_v2_files`. Catalog contract parsing and vector-map construction consumed much of this startup interval: `read_contract` accumulated 10.499 seconds, `VectorMap.from_map_v2` 10.528 seconds, and `VectorMap.__init__` 9.402 seconds. Pairwise proposal generation accumulated 5.767 seconds. Within it, `LocalFrame.__init__` ran 666 times and accumulated 5.374 seconds; `Transformer.from_crs` ran 1,338 times and accumulated 5.179 seconds. These timings identify repeated local-frame transformer setup as the clearest bounded optimization target while also showing that startup dominated this end-to-end partial window.

Before timeout, cProfile observed 64 proposal-ID calls, 28 accumulator-add calls, and 24 scorer evaluations. These are incomplete counters, not complete proposal coverage, unique candidate totals, or row completion. The profile therefore does not establish how many candidates the full row would evaluate, and it cannot be compared as a completed runtime benchmark.

## Approved optimization proposal

The approved implementation scope is limited to `bearing_localization/search/proposals/pairwise.py` plus `tests/accuracy/test_a43.py`. Add a bounded LRU keyed by the sorted catalog key pair. On a cache miss, calculate the current exact WGS84 inverse and geodesic midpoint, construct the same `LocalFrame`, and cache the frame plus both endpoint local coordinates. On a hit, reuse this deterministic pair geometry. LRU eviction only causes recomputation.

Keep report-pair outer traversal, sorted source/target traversal, both assignment order, stable-ID construction, proposal multiplicity, inclusive 2R query, exact candidate range checks, proposal-budget placement and budget accounting unchanged. Do not cap sources, neighbors, candidate generation, or scoring. Measure actual cache memory before setting the default capacity.

Parity coverage should compare cached and cache-disabled streams in exact order, including stable IDs, observation indices, catalog keys, coordinates, ranges, status, and multiplicity. Cases should cover multiple report pairs that revisit pairs, antimeridian and high-latitude coordinates, inclusive 2R boundary behavior, both directional assignments, exact range boundary, and budget exhaustion. Also run the existing A19/A28 and CLI proposal tests. Before/after timing must use the same frozen inputs under the shared benchmark lock; report complete bounded generator measurements separately from any watchdog-truncated end-to-end profile.
